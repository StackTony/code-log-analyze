# F002: 日志离线分析（M2 模块）

> Status: spec (v1 — 奉孝基于 07:18 UTC 铲屎官需求补充起草，用倾向立场作为默认决策；@文若 brainstorm + @云长 review 待走) | Owner: 奉孝 (@ragdoll-pa82, GLM-5.2, Siamese) | Reviewer: @云长（跨家族）

## Why

代码飞轮四模块架构里 M1（F001）已落地代码仓日志埋点图谱（LogPoint 主表 + CallContext + llm_hypothesis），M2 在此之上构建**离线 LLM 分析能力**，把"日志条目"转化为"可读的分析报告 + 可追溯的根因假设"。

铲屎官 2026-07-27 07:18 UTC 需求补充明确 M2 的核心动作是**两阶段 LLM 分析模式**：

> 利用LLM进行分析日志时，先默认对日志全量分析，给出整体性的分析报告（系统在做什么、哪里有问题、错误间的关联等等）。然后客户要求时再对某些行结合日志所在代码仓的解析的结果和全量分析报告的结果重点二次/多次进行深入LLM分析

**Phase 1 全量分析（默认）**：用户上传/输入日志 → LLM 整体性分析 → 产出系统行为总结 + 异常定位 + 错误关联报告。
**Phase 2 深入分析（按需）**：用户针对某些日志行触发 → 结合 M1 代码仓解析结果 + Phase 1 报告上下文 → LLM 二次/多次深入分析 → 回写 M1 LogPoint `llm_hypothesis`。

**前置依赖**：F001 已 merge（commit 87e2db9, 77 测试全绿），M1 对外 API 6 个方法 + LogPoint/CallContext 数据契约已稳定。F002 在 `packages/m2/` 新增子包，复用 `packages/contracts/` 数据契约，不修改 M1 service 层。

## What

### 一、模块定位

M2 是**离线 LLM 分析**层——输入是日志文本（用户上传或从 M3 在线扫描结果中抽取一段），输出是分析报告 + 深入分析假设。M2 不自建代码仓解析（依赖 M1 `query_log_points` + `get_call_context`），不实时流式处理（M3 在线扫描的职责）。

**与 F001 spec §437-439 现有定义的修订**：

| Feature | F001 spec 旧定义 | F002 v1 修订 |
|---------|-----------------|-------------|
| F002 | M2 离线分析 — 依赖 M1 query_log_points + LogPoint 主表 | **M2 离线 LLM 分析（两阶段）** — 依赖 M1 query_log_points + get_call_context + LogPoint.llm_hypothesis 字段 |
| F004 | M4 LLM 改进 — 依赖 get_call_context + llm_hypothesis | **M4 LLM 改进建议** — 基于 M2 Phase 2 深入分析结果生成修复 diff 建议（不再做"深入分析"本身，避免与 M2 重叠） |

**修订理由**：铲屎官需求补充明确"深入 LLM 分析"是 M2 的动作（"利用 LLM 进行分析日志时... 重点二次/多次进行深入 LLM 分析"），M4 应基于 M2 深入分析结果再做"改进"（修复建议/diff），不是 M2 的深入分析本身。F001 spec §439 原描述"M4 LLM 改进"语义不变，但澄清 M4 的"改进"=基于 M2 输出的二次加工，不是重新深入分析。

### 二、两阶段架构

```
┌─────────────────────────────────────────────────────────┐
│ Phase 1: 全量分析（默认触发）                            │
│ - 输入: 日志文本（用户上传 / M3 抽取一段）              │
│ - 动作:                                                  │
│   1. LogParser 解析日志条目（按格式 token 化）          │
│   2. LogPointMatcher 通过 log_message_template hash     │
│      匹配 M1 主表 LogPoint（已 ingested 状态）          │
│   3. 全量 LLM 调用（便宜模型，batch + 缓存）            │
│   4. 输出三类信息：                                      │
│      a. 系统行为总结（系统在做什么）                    │
│      b. 异常定位（哪里有问题，按模块/级别/时间分组）     │
│      c. 错误关联（错误传播链/因果关系）                  │
│ - 输出: AnalysisReport（持久化到 analysis_report 表）  │
│ - 成本控制:                                             │
│   * 时间窗兜底（默认 24h，配置 phase1_window_hours）    │
│   * 便宜模型（默认 gpt-4o-mini，配置 llm.phase1_model）│
│   * 复用 M1 Redis 缓存（key 含 phase1 + log_template）  │
└─────────────────────────────────────────────────────────┘
                          ↓ AnalysisReport
┌─────────────────────────────────────────────────────────┐
│ Phase 2: 深入分析（按需触发）                            │
│ - 输入:                                                  │
│   1. 用户选定的某些日志条目（line_id 列表）              │
│   2. M1 代码仓解析结果：                                │
│      - query_log_points(repo_id, filters) 取 LogPoint  │
│      - get_call_context(repo_id, fn_signature) 取调用链 │
│        + 同 community 案例 + evidence_refs              │
│   3. Phase 1 AnalysisReport 作为上下文背景              │
│ - 动作:                                                  │
│   1. 上下文组装（LogPoint + CallContext + Report +     │
│      选定日志条目原文）                                  │
│   2. 强模型 LLM 调用（默认 gpt-4，配置 llm.phase2_model）│
│   3. 产出深入分析：根因假设 + 修复建议 + 关联证据       │
│   4. 回写 M1 LogPoint.llm_hypothesis 字段              │
│      （M1 spec §三 L145 预留"confirmed 入库后必填"，   │
│       M2 Phase 2 是该字段的实际填充来源）              │
│ - 迭代性: 可二次/多次触发，累积上下文（Phase 2 报告     │
│   也持久化，下次 Phase 2 调用可引用前次结果）           │
│ - 输出: DeepAnalysisRecord（持久化到 deep_analysis     │
│   表，关联 line_id + log_point_id + report_id）         │
└─────────────────────────────────────────────────────────┘
```

### 三、数据契约

```python
@dataclass
class AnalysisReport:
    """Phase 1 全量分析报告 — M2 主输出。"""
    id: str                                # UUID
    repo_id: str | None                    # 关联代码仓（日志无 repo 时为 None）
    log_source: str                        # 日志来源标识（文件名/M3 流标识）
    log_line_count: int                    # 分析的日志条目数
    window_start: datetime | None         # 时间窗起点（按日志内时间戳）
    window_end: datetime | None
    model_name: str                        # phase1_model
    prompt_hash: str                       # prompt 版本追溯
    # 三类核心信息
    system_summary: str                    # 系统行为总结
    anomaly_localization: list[Anomaly]   # 异常定位
    error_correlation: list[ErrorChain]   # 错误关联
    # 元数据
    generated_at: datetime
    duration_seconds: float
    token_usage: TokenUsage
    ingestion_status: str                  # "draft" | "archived"


@dataclass
class Anomaly:
    """异常定位条目。"""
    line_ids: list[str]                    # 关联日志条目
    severity: str                          # "info" | "warn" | "error" | "critical"
    module: str | None                     # 模块/服务名
    summary: str                           # 一句话异常描述
    evidence_snippets: list[str]          # 日志原文片段


@dataclass
class ErrorChain:
    """错误关联链。"""
    chain_id: str
    line_ids_ordered: list[str]            # 按时间顺序的错误条目
    relation: str                          # "causal" | "correlation" | "propagation"
    summary: str                           # 链路描述
    confidence_score: float                # 0.0-1.0


@dataclass
class DeepAnalysisRecord:
    """Phase 2 深入分析记录。"""
    id: str                                # UUID
    report_id: str                         # 关联 Phase 1 报告
    line_ids: list[str]                    # 选定的日志条目
    log_point_ids: list[str]               # 关联 M1 LogPoint（通过 template 匹配）
    # 上下文引用
    call_contexts: list[CallContext]       # M1 get_call_context 结果快照
    # LLM 输出
    root_cause_hypothesis: str            # 根因假设
    fix_suggestion: str | None            # 修复建议（M4 改进模块的输入）
    related_evidence: list[CaseRef]       # 历史案例引用
    # 元数据
    model_name: str                        # phase2_model
    prompt_hash: str
    iteration: int                         # 第几次深入分析（1, 2, 3...）
    parent_record_id: str | None          # 前次深入分析 ID（累积上下文链）
    generated_at: datetime
    token_usage: TokenUsage


@dataclass
class TokenUsage:
    prompt_tokens: int
    completion_tokens: int
    total_cost_usd: float


@dataclass
class LogEntry:
    """解析后的单条日志条目（M2 输入单元）。"""
    line_id: str                            # UUID
    raw_text: str                          # 原始日志行
    timestamp: datetime | None             # 解析出的时间戳
    level: str | None                      # INFO/WARN/ERROR/DEBUG
    log_message_template: str | None       # 解析出的模板（用于匹配 M1 LogPoint）
    variables: dict[str, str]              # 模板变量值
    source_file: str | None
    source_line: int | None
```

### 四、对外 API 契约

```python
class LogAnalysisService:
    """M2 离线 LLM 分析服务（packages/m2/log_analysis_service.py）。"""

    def analyze_logs(
        self,
        log_source: LogSource,
        analyzer: User,
        repo_id: str | None = None,        # 关联代码仓（可选，有则启用 M1 关联）
        window_hours: int | None = None,   # 时间窗覆盖（None = 用配置默认 24h）
    ) -> AnalysisReport:
        """Phase 1 全量分析。
        - log_source: 文件路径 / 文本内容 / M3 流引用
        - 解析日志 → 匹配 M1 LogPoint（如有关联 repo）→ LLM 全量分析 → 持久化报告
        - 写 audit_log action=ACTION_PHASE1_ANALYZE
        """

    def deep_analyze(
        self,
        report_id: str,
        line_ids: list[str],
        analyzer: User,
        iteration_context: str | None = None,  # 用户补充上下文（可选）
    ) -> DeepAnalysisRecord:
        """Phase 2 深入分析。
        - 取 Phase 1 报告上下文 + M1 get_call_context（通过 log_message_template 匹配 LogPoint）
        - 强模型 LLM 调用 → 产出根因假设 + 修复建议
        - 回写 M1 LogPoint.llm_hypothesis（M1 spec §三 L145 预留）
        - 持久化 DeepAnalysisRecord（含 iteration + parent_record_id 链）
        - 写 audit_log action=ACTION_PHASE2_DEEP_ANALYZE
        """

    def get_report(self, report_id: str) -> AnalysisReport:
        """查 Phase 1 报告。"""

    def list_deep_analyses(
        self, report_id: str, line_id: str | None = None
    ) -> list[DeepAnalysisRecord]:
        """列 Phase 2 深入分析记录（可按 line 过滤）。"""

    def archive_report(self, report_id: str, archiver: User) -> None:
        """归档报告（draft → archived）。"""
```

### 十、与 M1 的关联机制

**LogPoint 匹配**：

```
M2 LogEntry.log_message_template  ←→  M1 LogPoint.log_message_template
（解析自运行时日志文本）            （解析自代码仓 AST）
```

匹配算法：
1. LogParser 从日志原文提取模板（如 `"User 12345 logged in"` → `"User {uid} logged in"`）
2. LogPointMatcher 计算 `hash(template)` 在 M1 主表查询
3. 匹配上 → 关联 `log_point_id`；匹配不上 → `log_point_id=None`（Phase 2 仍可分析，但不回写 M1）

**llm_hypothesis 回写**：

M1 spec §三 L145 `LogPoint.llm_hypothesis: LLMHypothesis | None # 候选阶段可空，confirmed 入库后必填`——M2 Phase 2 `deep_analyze` 是该字段的实际填充来源。回写流程：

```
Phase 2 deep_analyze 完成 →
  hypothesis_writer.write_back(log_point_ids, hypothesis) →
  M1 RepoLogGraphService.update_log_point_hypothesis(log_point_ids, hypothesis)
```

**M1 需新增方法** `update_log_point_hypothesis`（spec §五 F001 v1.1 修订附录追加，由 F002 实施时同步加）。这是个**M1 spec 微调**——不影响 M1 已合并代码的字节级稳定性，只在 `RepoLogGraphService` 加一个新方法（不修改已有 6 个方法）。

## Acceptance Criteria

- [ ] AC-1: `LogParser` 能解析至少 3 种日志格式（Python logging 默认 / JSON structured / syslog 风格），提取 timestamp/level/template/variables
- [ ] AC-2: `LogPointMatcher` 通过 `log_message_template` hash 匹配 M1 主表 LogPoint，匹配率 fixture 验证 ≥ 70%（无关模板 fallback 到 None）
- [ ] AC-3: Phase 1 `analyze_logs` 产出 `AnalysisReport` 含三类信息（system_summary / anomaly_localization / error_correlation），持久化到 `analysis_report` 表
- [ ] AC-4: Phase 1 时间窗兜底：`window_hours` 默认 24h，超出的日志条目截断 + 警告
- [ ] AC-5: Phase 1 LLM 调用经 LogSanitizer 脱敏（复用 M1 LogSanitizer），敏感字段零命中
- [ ] AC-6: Phase 1 LLM 调用复用 Redis 缓存（key 含 phase1 + log_template + model_name），相同日志重分析不重复调
- [ ] AC-7: Phase 2 `deep_analyze` 上下文组装含：选定日志条目原文 + M1 LogPoint + M1 CallContext + Phase 1 报告摘要
- [ ] AC-8: Phase 2 产出 `DeepAnalysisRecord` 持久化，含 `root_cause_hypothesis` + `fix_suggestion` + `related_evidence`
- [ ] AC-9: Phase 2 回写 M1 `LogPoint.llm_hypothesis` 字段（M1 加 `update_log_point_hypothesis` 方法）
- [ ] AC-10: Phase 2 迭代性：同 line 多次 `deep_analyze` 累积上下文（`iteration` 递增 + `parent_record_id` 链）
- [ ] AC-11: Phase 2 累积上限 `phase2_max_iterations`（默认 5）触发时拒绝新调用 + 提示归档重启
- [ ] AC-12: 5 个 HTTP endpoint 通过 TestClient 测试（status code + response schema）
- [ ] AC-13: 统一错误格式复用 F001.1 `error_handlers.py`（M2_* 错误码前缀）
- [ ] AC-14: 5 个 metrics 指标暴露在 9464 端口（m2_analysis_report_total 等）
- [ ] AC-15: 每个写操作（analyze/deep_analyze/archive）写 `audit_log` 表
- [ ] AC-16: P0 持久化铁律 — AnalysisReport + DeepAnalysisRecord + LogEntry 默认 TTL=0（用户可见产物）
- [ ] AC-17: 成本控制 — Phase 1 用便宜模型 + 批量 + 缓存；Phase 2 用强模型但限 iteration；`m2_llm_cost_usd_total` 累计可观测
- [ ] AC-18: 现有 139 个 M1+F001.1 测试无回归（不动 M1 service/storage/contracts 字节级，仅 M1 加 `update_log_point_hypothesis` 新方法）
- [ ] AC-19: 端到端 fixture 测试：用户上传日志 → Phase 1 报告 → 选 line → Phase 2 深入分析 → 验证 M1 LogPoint.llm_hypothesis 被回写

### C-1: 两阶段 LLM 分析模式（核心需求）

- **提出时间**：2026-07-27 07:18 UTC（需求补充）
- **背景**：F001 spec §437 原定义 M2 仅"离线分析"未细化分析模式；铲屎官需要明确 M2 的 LLM 分析流程。
- **客户需求**：
  - 利用 LLM 进行分析日志时，**先默认对日志全量分析**，给出整体性的分析报告
  - 报告含三类信息：① 系统在做什么（系统行为总结）② 哪里有问题（异常定位）③ 错误间的关联（错误传播链/因果关系）
  - **客户要求时**对某些行结合**代码仓解析结果 + 全量分析报告结果**重点**二次/多次进行深入 LLM 分析**
- **影响**：
  - M2 内部分两阶段架构（Phase 1 全量 + Phase 2 深入）
  - Phase 2 双源上下文（M1 解析结果 + Phase 1 报告）
  - Phase 2 迭代性（二次/多次）
  - 回写 M1 LogPoint.llm_hypothesis 字段
  - M4 改进模块基于 M2 Phase 2 输出，不重叠深入分析动作
- **落地点**：spec §一 模块定位（M4 边界修订）、§二 两阶段架构、§三 数据契约（AnalysisReport + DeepAnalysisRecord）、§四 对外 API（analyze_logs + deep_analyze）、AC-3/7/8/9/10/11、实施计划 Phase 1 + Phase 2 task

### C-2: 客户"二次/多次"深入分析的累积上下文

- **提出时间**：2026-07-27 07:18 UTC（需求补充，"二次/多次"措辞）
- **背景**：铲屎官明确 Phase 2 不是一次性动作，可重复触发。
- **客户需求**：深入分析可多次进行，每次都基于前次结果。
- **影响**：
  - `DeepAnalysisRecord.iteration` 字段递增

  - 同 line 多次调用累积上下文，AC-10/11 验证
- **落地点**：spec §三 DeepAnalysisRecord 字段、§四 deep_analyze 迭代语义、AC-10/11、实施计划 deep_analyzer task

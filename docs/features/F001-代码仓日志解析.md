# F001: 代码仓日志解析模块

> Status: spec (v5 — 云长 round-1 review 4 条 Must-Fix 修复) | Owner: 奉孝 (@ragdoll-pa82, GLM-5.2) | Reviewer: @云长（跨家族）

## Why

代码飞轮项目的四个模块（解析/离线分析/在线扫描/改进）依赖同一份"代码仓日志埋点图谱"作为底座。本 feature 构建 M1：从代码仓中识别所有日志埋点，抽取确定性上下文 + LLM 推断打印原因，经用户筛选后入库为 M2/M3/M4 提供查询面。

**实现语言决策**：Python。理由：(1) gitnexus 是 MCP 工具，Python 通过 MCP client 调用比 TS 顺；(2) tree-sitter 在 Python 生态更成熟（py-tree-sitter / tree-sitter-languages 包）；(3) 数据契约用 Python dataclass，类型化 + 可序列化；(4) cat-cafe SOP 默认 TS 工程基线（pnpm/Biome）但**本 feature 是后端服务**，SOP 的 TS 基线适用于前端子模块（F003 UI），不约束 M1 后端。Python 工程基线：ruff（lint + format）+ pytest。

## What

### 一、模块定位

M1 不自建 AST / 不自建 call graph——**用 gitnexus 做 graph backend，M1 只做日志埋点识别 + 字段抽取 + LLM 推断 + 候选筛选**。

### 二、四子单元架构

```
┌─────────────────────────────────────────────────┐
│ Unit A: Repo Registrar                           │
│ - 输入: repo_url | local_path                    │
│ - 动作: gitnexus analyze --name <alias> <path>   │
│ - 输出: repo_id + gitnexus_repo_alias            │
│ - 安全: URL 白名单(https only) + 本地路径沙箱    │
│ - 状态: repo_ingest_lock 表 (running/done/failed)│
│         并发请求返回"已在解析中"，幂等            │
│ - 增量: 支持 --incremental 模式 (调              │
│         gitnexus detect_changes)，v1 可只留接口  │
│                                                  │
│ 状态机规则（云长 MF-3 修复，写入 spec 真相源）：│
│ - running → done: ingest 正常完成                 │
│ - running → failed: 进程崩溃 / 超时 / 手动 force │
│   * 超时阈值 = config.ingest_timeout_minutes     │
│     (默认 30 min)，running 无心跳超过此值         │
│     → 下次 ingest_repo 调用清理为 failed         │
│   * 进程崩溃 = 进程退出但 lock 仍 running        │
│     → 同上，由下次 ingest_repo 启动时清理         │
│ - failed → running: 用户重新调 ingest_repo       │
│   (新建 RepoIngestLockModel 记录，幂等)           │
│ - force_release_lock admin API:                  │
│   * 仅 admin role (User.is_admin=True) 可调      │
│   * 强制把 running 状态的 lock 转 failed         │
│   * 写 audit_log action=ACTION_FORCE_RELEASE_LOCK│
│   * 用于清理已知死锁（如 ingest 进程卡死且无心跳） │
└─────────────────────────────────────────────────┘
                       ↓ repo_id
┌─────────────────────────────────────────────────┐
│ Unit B: Log Point Finder (M1 核心)               │
│ - 输入: repo_id                                  │
│ - 动作 (两层过滤):                                │
│   Layer 1 (cypher 粗筛):                         │
│     MATCH (a)-[:CALLS]->(b:Function)             │
│     WHERE b.name =~                              │
│       '^(log|print|printf|fprintf|syslog|        │
│         logging|logger|warn|error|debug|        │
│         trace).*$'                               │
│     RETURN 候选 LogPoint                          │
│   Layer 2 (tree-sitter 精筛):                    │
│     对粗筛结果逐个解析调用点 AST                  │
│     - 确认 callee 属于白名单日志框架              │
│       (logging/loguru/printf/syslog) 或           │
│       自定义日志函数 (repo 内命名匹配              │
│       ^.*_(log|error|debug|trace).*$)            │
│     - 抽取行号/函数签名/调用链                    │
│     - 计算 confidence_score (见数据契约)          │
│   再调 gitnexus context() 取调用链上下文           │
│ - 输出: List[LogPoint]（候选池，未持久化）        │
│ - 去重键: (repo_id, file_path, line_start)       │
└─────────────────────────────────────────────────┘
                       ↓ List[LogPoint]
┌─────────────────────────────────────────────────┐
│ Unit C: LLM Hypothesis Generator                 │
│ - 输入: List[LogPoint]（候选）                   │
│ - 动作:                                          │
│   1. LogSanitizer 扫脱敏:                        │
│      - 密钥/api_key/password/token 正则           │
│      - IPv4/IPv6 地址                             │
│      - 邮箱                                       │
│      - 命中数>0 → 替换为 [REDACTED_*]             │
│   2. 批量调 LLM 生成"打印原因"假设               │
│   3. 填充 error_kind 分类                        │
│ - 输出: LogPoint.llm_hypothesis 填充             │
│ - 节流: Redis 缓存 key =                          │
│   hash(log_template + enclosing_function_signature│
│        + model_name + extractor_version)         │
│   model 升级时 model_name 变 → 旧缓存自动失效     │
│   extractor 升级时 extractor_version 变 → 旧缓存失效│
└─────────────────────────────────────────────────┘
                       ↓ List[LogPoint]（带 LLM 假设）
┌─────────────────────────────────────────────────┐
│ Unit D: Candidate Staging + Ingestion Gate       │
│ - 输入: List[LogPoint]（带 LLM 假设）            │
│ - 动作:                                          │
│   1. 写候选池(candidate_staging 表，不进主表)    │
│   2. occurrence_count =                          │
│      同 log_template 在仓内被识别为 LogPoint 次数 │
│   3. 标记 is_top_n: 按 occurrence_count 倒序     │
│      前 N (N=config.top_n_candidates, 默认 50)    │
│   4. 等用户在 UI 筛选 → confirm → 入主表         │
│   5. 候选池 TTL 清理:                            │
│      ingestion_status='candidate' AND             │
│      last_seen_at < now()-TTL(默认 30 天)         │
│ - 输出: 候选池状态                               │
└─────────────────────────────────────────────────┘
```

### 三、LogPoint 数据契约

```python
@dataclass
class LogPoint:
    id: str                              # UUID
    repo_id: str
    git_commit_sha: str                  # 解析时仓当前 commit，schema 演化判断 LogPoint 过期
    extractor_version: str               # "1.0.0" — 解析器版本，升级时用于判断旧 LogPoint 是否重解析
    file_path: str                       # 统一 POSIX 风格（正斜杠），无论解析平台
    function_signature: str              # 来自 gitnexus Function 节点
    line_start: int
    line_end: int
    language: str                        # 字符串 + 枚举常量 LANGUAGE_C / LANGUAGE_PYTHON，便于扩展
    log_level: str                        # INFO/WARN/ERROR/DEBUG/UNKNOWN
    log_message_template: str            # "User {uid} logged in"
    log_message_variables: list[str]     # ["uid"]
    framework_hint: str                 # "logging" | "loguru" | "printf" | "syslog" | "custom"
    confidence_score: float              # 0.0-1.0，logging.info=1.0 / 裸 print=0.5 / 自定义=0.7

    # --- 确定性上下文（来自 gitnexus）---
    enclosing_class: str | None
    call_chain_to_entry: list[str]       # gitnexus context() 取
    enclosing_community: str | None     # gitnexus community label

    # --- 历史案例推荐（确定性）---
    evidence_refs: list[CaseRef]         # 同 community + 同 log_template 的过往案例

    # --- LLM 推断（每条候选都跑）---
    llm_hypothesis: LLMHypothesis | None # 候选阶段可空，confirmed 入库后必填

    # --- 频次 + 入库状态 ---
    occurrence_count: int                # 同 log_template 在仓内被识别为 LogPoint 的次数（静态分析，M1 内闭环）
    is_top_n: bool                       # 按 occurrence_count 倒序前 N 标记，N=config.top_n_candidates
    ingestion_status: str                # "candidate" | "confirmed" | "ingested" + 常量枚举
    first_seen_at: datetime
    last_seen_at: datetime


@dataclass
class LLMHypothesis:
    summary: str                         # 一句话假设
    possible_causes: list[str]           # 可能触发原因列表
    error_kind: str                      # 错误分类: "param_error"|"state_error"|"external_dep_error"|"logic_error"|"unknown"
    suggested_check: str | None          # 建议人工核查点（可选）
    model_name: str                      # 用了哪个模型，便于追溯
    prompt_hash: str                     # 用哪个 prompt 版本生成的（A/B 测试追溯）
    generated_at: datetime


@dataclass
class CaseRef:
    case_id: str
    repo_id: str
    file_path: str
    function_signature: str
    log_template: str
    resolved_at: datetime
    resolution_summary: str              # 一句话当时怎么解决
    resolution_diff_url: str | None     # 修代码 PR/diff 链接


@dataclass
class RepoIngestLock:
    repo_id: str
    status: str                          # "running" | "done" | "failed"
    started_at: datetime
    finished_at: datetime | None
    error_msg: str | None
    ingester: str                        # user_id


@dataclass
class CallContext:
    """get_call_context() 返回值 — M4 LLM 改进模块依赖此契约"""
    function_signature: str
    callers: list[str]                   # 调用方函数签名列表（谁调用了本函数）
    callees: list[str]                   # 被调函数列表（本函数调用了谁）
    enclosing_community: str | None     # gitnexus community label
    related_log_points: list["LogPoint"] # 同 community 的其他 LogPoint
    evidence_refs: list[CaseRef]         # 历史案例
```

### 四、日志调用识别规则（Unit B）

| 语言 | 框架 | 识别模式 |
|------|------|---------|
| Python | logging | `logging.info/warn/error/debug/warning/critical/exception(` | confidence=1.0 |
| Python | loguru | `logger.<level>(` | confidence=1.0 |
| Python | 裸 print | `print(`（**默认不识别**；仅当 config `include_print=True` 时纳入；confidence=0.5） | confidence=0.5 |
| C | stdio | `printf(`/`fprintf(stdout/stderr,` | confidence=1.0 |
| C | syslog | `syslog(` | confidence=1.0 |
| C | 自定义 | 同 repo 内命名匹配 `^.*_(log|error|debug|trace).*$` 的函数调用 | confidence=0.7 |

**过滤规则**：注释行、字符串字面量内的"log"关键字不识别；只识别真实函数调用。

```python
class RepoLogGraphService:
    def ingest_repo(
        self, source: RepoSource, ingester: User,
        incremental: bool = False  # F001 v1 可只留接口，raise NotImplementedError
    ) -> RepoId:
        """clone+gitnexus analyze+候选池构建一步到位

    def list_candidates(
        self, repo_id: RepoId, filter: CandidateFilter
    ) -> list[LogPoint]:
        """用户筛选 UI 调用：列高频候选（默认按 is_top_n=True 过滤，可切换查看全部）"""

    def confirm_ingestion(
        self, repo_id: RepoId, log_point_ids: list[str], confirmer: User
    ) -> None:
        """用户勾选后调，候选 → 主表（P0 持久化铁律：用户 opt-in 才入库）"""

    def revoke_ingestion(
        self, repo_id: RepoId, log_point_ids: list[str], revoker: User
    ) -> None:
        """反向操作：已入主表的 LogPoint 撤回候选池（first-class API）
        审计日志记录撤销原因

        云长 MF-2 修复后语义：revoke 不删主表记录（违反 P0 持久化铁律），
        改为状态机回退 ingestion_status: ingested/confirmed → candidate。
        保留主表记录可追溯历史；query_log_points 自动过滤 candidate 状态。"""

    def query_log_points(
        self, repo_id: RepoId, filters: LogPointFilter
    ) -> list[LogPoint]:
        """M2 调用：查主表（仅 ingested 状态）"""

    def get_call_context(
        self, repo_id: RepoId, function_signature: str
    ) -> CallContext:
        """M4 调用：通过 gitnexus context() 取调用链 + 同 community 案例"""

    def force_release_lock(
        self, repo_id: RepoId, admin: User
    ) -> None:
        """云长 MF-3 修复 — spec §五补此方法声明（plan T6 已有实现）
        admin only：强制把 running 状态的 repo_ingest_lock 转 failed，
        用于清理已知死锁（如 ingest 进程崩溃且无心跳）。
        非 admin 调用 raise PermissionError。
        写 audit_log action=ACTION_FORCE_RELEASE_LOCK。"""
```

## Acceptance Criteria

- [ ] AC-1: Unit A 能接收 GitHub URL 或本地路径，调 `gitnexus analyze` 完成建图，返回 `repo_id`
- [ ] AC-2: Unit A 拒绝 `..` 越权路径与非 https URL（含测试用例验证拒绝）
- [ ] AC-3: Unit B 对 6 种 pattern 各有 fixture 测试（Python logging / loguru / 裸 print / C printf / C syslog / C 自定义函数名），能识别出 LogPoint 并正确填充确定性字段

- [ ] AC-12: LLM key 通过配置文件注入（`config.local.yaml` 的 `llm.api_key` 字段或环境变量 `CODEFLY_LLM_API_KEY`），代码中无硬编码 key

### C-2: 第一版支持 C 和 Python 两种语言

### C-3: 用 gitnexus 工具做代码解析（不重建 AST / call graph）

- **提出时间**：2026-07-24 03:44 UTC
- **背景**：自建 AST + call graph 工作量大且重复造轮子；gitnexus 已是成熟 graph backend。
- **客户需求**：M1 不自建 AST、不自建 call graph——用 gitnexus 做 graph backend，M1 只做日志埋点识别 + 字段抽取 + LLM 推断 + 候选筛选。
- **影响**：
  - 架构边界：M1 通过 MCP client 调 gitnexus（cypher 粗筛 CALLS 边 + context() 取调用链 + impact() 取影响面），不维护自己的 graph schema

### C-4: 每条日志埋点必须含 LLM 推断的打印原因假设

- **提出时间**：2026-07-24 03:44 UTC
- **背景**：确定性信息（文件/函数/行号/历史案例）只是定位，不能告诉运维"这条日志为什么打"。
- **客户需求**：代码仓的每条日志埋点除了有文件位置、函数名、行号、相关历史案例推荐等确定性信息外，**还要有 LLM 介入给出打印日志的可能原因**。
- **影响**：
  - `LogPoint.llm_hypothesis: LLMHypothesis | None` 字段必填（候选阶段可空，confirmed 入库后必填）
  - `LLMHypothesis` 结构：summary / possible_causes / error_kind / suggested_check / model_name / prompt_hash / generated_at
  - Unit C 专门跑 LLM 批量调用 + Redis 缓存
  - LLM 假设定位为"参考假设"——M4 LLM 改进模块基于此但**不作为自动改代码依据**（避免幻觉风险）
- **落地点**：spec §三 LogPoint/LLMHypothesis 数据契约、§二 Unit C、Risk 表「LLM 输出幻觉」条目、AC-6/AC-7/AC-8、实施计划 T9-T10

### C-5: 高频日志由用户决定后再入库（不全部存入数据库）

- **提出时间**：2026-07-24 03:44 UTC
- **背景**：一个大型仓可能含数千条日志埋点，全部入库 → 噪音 + 存储 + 后续分析成本爆炸。
- **客户需求**：高频日志可以让用户决定后再存入数据库，不需要全部存入。
- **影响**：
  - 两阶段入库：候选池（candidate_staging 表）→ 用户在 UI 勾选 confirm → 主表（log_point 表）
  - `ingestion_status` 状态机：`candidate → confirmed → ingested`，可逆（`revoke_ingestion`）
  - P0 持久化铁律：用户可见、可追溯、可恢复预期的数据默认 TTL=0；**只有用户 opt-in 才入主表**，无 confirm 路径直接写主表 = P0 bug
  - `is_top_n` 标记帮用户优先看高频候选（按 `occurrence_count` 倒序前 N）
- **落地点**：spec §二 Unit D、§三 ingestion_status 字段、§五 API 契约（confirm_ingestion/revoke_ingestion）、AC-9/AC-10/AC-11、实施计划 T11（CandidateStager）

### C-6: LLM key 通过配置文件注入（铲屎官有地方写 key）

- **提出时间**：2026-07-24 06:18 UTC

- **客户需求**：铲屎官需要有一个固定地方写 LLM key——优先通过配置文件 `config.local.yaml`（gitignored），环境变量作为兜底。

  - `llm.api_key: ${CODEFLY_LLM_API_KEY}` —— 配置文件中用环境变量占位符，实际 key 由环境变量注入
  - `config.example.yaml`（入库）提供模板；`config.local.yaml`（gitignored）由铲屎官本地填写

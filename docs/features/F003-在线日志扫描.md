# F003: 日志在线扫描（M3 模块）

> Status: spec (v1 — 奉孝基于 F002 spec §495 后续 Phase 规划起草，用倾向立场作为默认决策；@文若 brainstorm + @云长 review 待走) | Owner: 奉孝 (@ragdoll-pa82, GLM-5.2, Siamese) | Reviewer: @云长（跨家族，待请求）

## Why

代码飞轮四模块架构里 M1（F001）已落地代码仓日志埋点图谱，M2（F002，已 merge origin/main `3040c61`）已落地离线 LLM 两阶段分析能力（Phase 1 全量报告 + Phase 2 深入分析回写 M1 `llm_hypothesis`）。M3 在此之上构建**在线日志扫描能力**，把"用户主动上传日志"扩展到"系统持续监控流式日志 + 自动触发分析"。

铲屎官 2026-07-27 07:18 UTC F002 需求补充里明示「利用 LLM 进行分析日志时，先默认对日志全量分析」——M2 已落地"全量分析"动作。M3 的核心动作是**让全量分析持续化、自动化**：

- **M2 离线**：用户上传日志文本 → LLM 分析 → 报告。**一次性、批量、用户驱动**。
- **M3 在线**：实时流式日志 → 持续监控 + 触发条件 → 调 M2 `analyze_logs` → 报告。**持续、流式、系统驱动**。

**前置依赖**：F001 + F001.1 + F002 已 merge origin/main（`3040c61`），M1 LogPoint 主表 + M2 LogAnalysisService 5 个 API 方法已稳定。F003 在 `packages/m3/` 新增子包，复用 `packages/contracts/` 数据契约 + M2 LogParser/LogPointMatcher/LogAnalysisService，不修改 M1/M2 service 层。

**F001 spec §438 原定义修订**：

| Feature | F001 spec 旧定义 | F003 v1 修订 |
|---------|-----------------|-------------|
| F003 | M3 在线扫描 — 依赖 `query_log_points` + 候选池状态 | **M3 在线日志扫描** — 依赖 M2 `LogAnalysisService.analyze_logs`（触发）+ M1 LogPoint 主表（template 匹配，不依赖候选筛选流程）|

**修订理由**：F001 spec §438 原写"依赖候选池状态"——那是 M1 ingestion 的 user action（用户主动 promote candidate → confirmed）。M3 在线扫描是**消费**已 confirmed 的 LogPoint 主表做模板匹配（同 M2 路径），不参与 candidate 筛选流程。"依赖 query_log_points" 仍成立（M3 通过 M2 LogPointMatcher 间接走 M1 主表查询）。

## What

### 一、模块定位

M3 是**在线日志扫描**层——输入是实时流式日志（file tail / HTTP webhook 推送），输出是 `LogStreamEvent` 累积 + `ScanTrigger` 触发记录 + 调用 M2 `analyze_logs` 产出的 `AnalysisReport`。M3 不自建 LLM 分析逻辑（依赖 M2 LogAnalysisService），不修改 M1 主表（仅读 LogPoint 做匹配）。

**与 M2 的职责切分**：

| 维度 | M2 离线分析 | M3 在线扫描 |
|------|------------|------------|
| 输入 | 用户上传文本 | 实时流式日志（file/webhook） |
| 触发 | 用户主动 | 系统自动（时间窗/异常密度/手动） |
| LLM 调用 | 自己调 | 不直接调，触发 M2 |
| 持久化 | AnalysisReport + DeepAnalysisRecord + LogEntry | LogStreamSource + LogStreamEvent + ScanTrigger |
| 与 M1 关系 | 回写 LogPoint.llm_hypothesis（Phase 2） | 只读 LogPoint 做匹配（template hash） |
| 时效 | 一次性 | 持续 + 增量 |

**与 M4 的边界**（F004 改进模块，未启动）：M4 基于 M2 Phase 2 DeepAnalysisRecord 输出修复建议，**不与 M3 直接交互**。M3 触发 M2 产报告后，M4 可消费 M2 DeepAnalysisRecord（不依赖 M3）。

### 二、流式架构

```
┌─────────────────────────────────────────────────────────┐
│ M3 数据源（LogStreamSource）                            │
│ - kind: "file_tail" | "http_webhook"                    │
│ - 状态: active | paused | stopped                      │
│ - 关联 repo_id（可选，启用 M1 LogPoint 匹配）          │
└──────────────┬─────────────────────────┬───────────────┘
               │                          │
       file_tail 模式                http_webhook 模式
       (本地文件 tail)               (POST /ingest 推送)
               │                          │
               ▼                          ▼
┌─────────────────────────────────────────────────────────┐
│ LogStreamEvent 累积（packages/m3/event_ingestor.py）  │
│ - 解析复用 M2 LogParser（不重新实现）                  │
│ - 提取 timestamp / level / template / variables       │
│ - LogPointMatcher 复用 M2 同款（template hash 匹配）    │
│ - 匹配上 → 填 log_point_id（M1 confirmed LogPoint）   │
│ - 匹配不上 → log_point_id=None，仍入库（仅作原始事件） │
│ - 持久化到 log_stream_event 表                         │
└────────────────────┬────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────────┐
│ 触发判定（packages/m3/trigger_evaluator.py）          │
│ 三种触发条件（任一满足 → 调 M2 analyze_logs）：        │
│ 1. time_window: 累积 N 条或 T 时间（默认 1000 条/5min，│
│    任一满足即触发，参见 AC-5）                          │
│ 2. anomaly_density: error 级别占比 > 阈值（默认 30%）  │
│ 3. manual: 用户主动 POST /sources/{id}/scan-now        │
│    （service 方法 scan_now，参见 §四 API）             │
│ - 写 ScanTrigger 记录（trigger_kind + event_count）   │
│ - 调 M2 LogAnalysisService.analyze_logs(              │
│     log_source=LogSource.from_stream_window(...),     │
│     analyzer=scanner_user,                             │
│     repo_id=source.repo_id,                           │
│   ) → 拿 AnalysisReport.id                             │
│ - 回填 ScanTrigger.triggered_report_id                 │
│ - 写 audit_log action=ACTION_M3_TRIGGER_ANALYZE       │
└─────────────────────────────────────────────────────────┘
```

### 三、数据契约

```python
@dataclass
class LogStreamSource:
    """M3 数据源配置。"""
    id: str                                # UUID
    kind: str                              # "file_tail" | "http_webhook"
    config: dict                           # kind-specific 配置
    # file_tail: {"path": "/var/log/app.log", "pos_file": ".pos"}
    # http_webhook: {"path": "/ingest/{source_id}", "auth_token": "..."}
    repo_id: str | None                    # 关联代码仓（可选，启用 M1 LogPoint 匹配）
    ingestion_status: str                  # "active" | "paused" | "stopped"
    created_at: datetime
    updated_at: datetime


@dataclass
class LogStreamEvent:
    """M3 流式日志事件（解析后）。"""
    id: str                                # UUID
    source_id: str                         # 关联 LogStreamSource
    raw_text: str                          # 原始日志行
    # 解析后字段（复用 M2 LogParser 提取）
    timestamp: datetime | None            # 解析出的时间戳
    level: str | None                     # INFO/WARN/ERROR/DEBUG
    log_message_template: str | None       # 解析出的模板（用于匹配 M1 LogPoint）
    variables: dict[str, str]              # 模板变量值
    # M1 关联
    log_point_id: str | None              # 匹配 M1 LogPoint 后填充（None=未匹配）
    # 元数据
    ingested_at: datetime                  # M3 入库时间（区别于日志自身 timestamp）


@dataclass
class ScanTrigger:
    """M3 触发 M2 分析的记录。"""
    id: str                                # UUID
    source_id: str                         # 关联 LogStreamSource
    trigger_kind: str                      # "time_window" | "anomaly_density" | "manual"
    event_count: int                       # 本次触发覆盖的事件数
    window_start: datetime                 # 窗口起点（按 LogStreamEvent.ingested_at）
    window_end: datetime
    # M2 关联
    triggered_report_id: str | None        # 调 M2 后回填（失败则 None）
    triggered_at: datetime
    triggered_by: str                      # user_id（manual）或 "system"（auto）
```

### 四、对外 API 契约

```python
class OnlineLogScanner:
    """M3 在线日志扫描服务（packages/m3/online_log_scanner.py）。"""

    def register_source(
        self,
        kind: str,
        config: dict,
        repo_id: str | None,
        user: User,
    ) -> LogStreamSource:
        """注册数据源（kind=file_tail/http_webhook）。
        - file_tail: 启动后台 tail task（polling 模式 v1，inotify 可选 v2）
        - http_webhook: 注册 POST 路由 /ingest/{source_id}
        - 写 audit_log action=ACTION_M3_REGISTER_SOURCE
        """

    def list_sources(
        self, status: str | None = None,
    ) -> list[LogStreamSource]:
        """列数据源（可按状态过滤）。"""

    def pause_source(self, source_id: str, user: User) -> None:
        """暂停数据源（file_tail 停 tail，webhook 返回 410 Gone）。
        - 不丢累积事件
        - 写 audit_log action=ACTION_M3_PAUSE_SOURCE
        """

    def resume_source(self, source_id: str, user: User) -> None:
        """恢复数据源。"""

    def ingest_event(
        self, source_id: str, raw_text: str,
    ) -> LogStreamEvent:
        """HTTP webhook 入口（外部系统推送单条日志）。
        - 解析复用 M2 LogParser
        - 匹配 M1 LogPoint（LogPointMatcher 复用 M2 同款）
        - 持久化 LogStreamEvent
        - 写 audit_log action=ACTION_M3_INGEST_EVENT
        """

    def scan_now(
        self, source_id: str, user: User,
    ) -> AnalysisReport:
        """手动触发 M2 analyze_logs（基于当前累积事件）。
        - 取 source 当前未触发的事件窗口
        - 调 M2 LogAnalysisService.analyze_logs
        - 写 ScanTrigger(trigger_kind="manual")
        - 写 audit_log action=ACTION_M3_SCAN_NOW
        - 返回 M2 AnalysisReport
        """

    def list_events(
        self, source_id: str, time_range: TimeRange,
    ) -> list[LogStreamEvent]:
        """列事件（可按时间窗过滤）。"""

    def list_triggers(
        self, source_id: str, time_range: TimeRange | None = None,
    ) -> list[ScanTrigger]:
        """列触发记录。"""
```

### 十、与 M1/M2 的关联机制

**M1 LogPoint 匹配**（与 M2 同款路径）：

```
M3 LogStreamEvent.log_message_template  ←→  M1 LogPoint.log_message_template
（LogParser 从流式日志解析）              （M1 主表，已 confirmed 状态）
```

匹配算法：
1. `LogParser` 从日志原文提取模板（复用 M2 `LogParser`）
2. `LogPointMatcher` 计算 `hash(template)` 在 M1 主表查询（复用 M2 `LogPointMatcher` + `StorageBackedLogPointIndex`）
3. 匹配上 → 填 `log_point_id`；匹配不上 → `log_point_id=None`（仍入库，仅作原始事件）

**M2 触发协议**：

```
M3 ScanTrigger 触发 →
  LogSource.from_stream_window(source_id, window_start, window_end) →
  M2 LogAnalysisService.analyze_logs(log_source, analyzer, repo_id) →
  M2 持久化 AnalysisReport →
  M3 回填 ScanTrigger.triggered_report_id
```

**关键约束**：
- M3 不直接 import M2 service，通过依赖注入（`m2_service: M2ServiceProtocol`）
- M3 不修改 M2 数据契约，仅消费 `AnalysisReport` 返回值
- M3 不回写 M1 主表（仅 LogPointMatcher 读匹配，不改 LogPoint.llm_hypothesis——那是 M2 Phase 2 的职责）

## Acceptance Criteria

- [ ] AC-1: `file_tail` 数据源能 tail 跟踪本地日志文件增量（polling 模式，v1 默认），文件轮转/截断不丢数据（位置 checkpoint 到 `.pos` 文件）
- [ ] AC-2: `http_webhook` 数据源接受 POST 推送日志条目（单条 + batch），返回 `LogStreamEvent` 解析结果
- [ ] AC-3: `LogStreamEvent` 解析复用 M2 `LogParser`（不重新实现），提取 timestamp/level/template/variables
- [ ] AC-4: `LogPointMatcher` 复用 M2 同款（template hash 匹配 M1 LogPoint），匹配率 fixture 验证 ≥ 70%
- [ ] AC-5: 时间窗触发（默认累积 1000 events **或** 5min 窗口，任一满足即触发）→ 调 M2 `LogAnalysisService.analyze_logs`，`ScanTrigger(trigger_kind="time_window")` 持久化
- [ ] AC-6: 异常密度触发（error 级别占比 > 30% 阈值）→ 调 M2 `analyze_logs`，`ScanTrigger(trigger_kind="anomaly_density")` 持久化
- [ ] AC-7: 手动 `scan_now` → 调 M2 `analyze_logs`，`ScanTrigger(trigger_kind="manual")` 持久化
- [ ] AC-8: `ScanTrigger` 记录持久化（含 `triggered_report_id` 关联 M2 报告），可按 source_id + 时间窗查询
- [ ] AC-9: `pause_source` / `resume_source` 不丢累积事件（`pause_source_keep_events=True`），file_tail 停 tail，webhook 返回 410 Gone
- [ ] AC-10: 8 个 HTTP endpoint 通过 TestClient 测试（status code + response schema）
- [ ] AC-11: 错误码 `M3_*` 前缀（复用 F001.1 `error_handlers.py`）
- [ ] AC-12: 5 个 metrics 指标暴露在 9464 端口（`m3_events_ingested_total` 等）
- [ ] AC-13: 每个写操作（register/pause/resume/ingest/trigger/scan_now）写 `audit_log` 表
- [ ] AC-14: P0 持久化铁律 — `LogStreamSource` + `LogStreamEvent` + `ScanTrigger` 默认 TTL=0（用户可见产物）
- [ ] AC-15: 成本控制 — M3 触发 M2 时复用 M2 Phase 1 缓存（相同日志窗口不重复 LLM 调用）+ 触发频次配置上限

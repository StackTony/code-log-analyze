# F002 设计输入：M2 离线分析 — 两阶段 LLM 分析模式

> 铲屎官 2026-07-27 07:18 UTC 需求补充，奉孝整理理解 + 设计提案 + 开放问题。
> 本文档**不是 spec**，是 spec 启动前的设计探索产出，待铲屎官确认理解 + 开放问题关闭后再进 F002 spec v1。

## 一、铲屎官原文

> 利用LLM进行分析日志时，先默认对日志全量分析，给出整体性的分析报告（系统在做什么、哪里有问题、错误间的关联等等）。然后客户要求时再对某些行结合日志所在代码仓的解析的结果和全量分析报告的结果重点二次/多次进行深入LLM分析

## 二、需求拆解（奉孝理解）

### 拆解为两阶段 LLM 分析模式

**Phase 1 — 全量分析（默认）**
- 输入：日志全量（边界待定，见开放问题 Q2）
- LLM 动作：整体性分析
- 输出：分析报告，含三类信息
  1. **系统在做什么** — 系统行为总结（业务流程概述）
  2. **哪里有问题** — 异常/错误定位（按错误级别/模块/时间段分组）
  3. **错误间的关联** — 错误传播链/因果关系（如 service A 超时 → service B 重试失败 → service C 雪崩）
- 触发：默认（不需要客户主动要求）
- 持久化：报告本身是用户可见产物 → P0 持久化铁律 → TTL=0

**Phase 2 — 深入分析（按需）**
- 触发：客户要求时（具体触发方式见 Q3）
- 范围：某些行（特定日志条目）
- 输入上下文（双源）：
  1. **日志所在代码仓的解析结果** — M1 `query_log_points` + `get_call_context` 提供（LogPoint + CallContext + evidence_refs 历史案例）
  2. **Phase 1 全量分析报告结果** — 作为深入分析的"上下文背景"（不是从零分析，是基于已知整体图景）
- LLM 动作：二次或多次深入分析
- 迭代性："二次/多次" 暗示可重复触发，可能累积上下文（每次深入分析都基于前次结果）

## 三、关联 M1 数据契约（已有基础）

F001 spec §五已定义 M1 对外 API，F002 直接消费：

| M1 API | F002 用途 |
|--------|----------|
| `query_log_points(repo_id, filters)` | 通过 `log_message_template` 匹配运行时日志条目 → 找到对应的 LogPoint（代码仓里的日志埋点定义） |
| `get_call_context(repo_id, function_signature)` | 拿调用链 + 同 community 案例 + `evidence_refs` 历史案例 |

**关键关联点**：运行时日志条目如何关联到 M1 LogPoint？

- 运行时日志条目（M2 输入）：含 `log_message_template`（如 `"User {uid} logged in"`）
- M1 LogPoint（M1 主表）：含 `log_message_template`（同字段）
- 匹配：通过 `log_message_template` 模板字符串 hash 匹配 → 找到代码仓里的埋点位置
- 这是 F001 spec §三 L131 `log_message_template` 字段的设计意图（M1 早就为 M2 留了接口）

## 四、M2/M3/M4 边界推断（待确认）

F001 spec §437-439 现有定义：

| Feature | 模块定位 | 依赖 |
|---------|---------|------|
| F002 | M2 离线分析 | M1 `query_log_points` + LogPoint 主表 |
| F003 | M3 在线扫描 | M1 `query_log_points` + 候选池状态 |
| F004 | M4 LLM 改进 | M1 `get_call_context` + `llm_hypothesis` |

**铲屎官这次需求补充暴露的边界问题**：

铲屎官说的"对某些行结合日志所在代码仓的解析结果 + 全量分析报告 → 深入 LLM 分析"——这动作是 M2 还是 M4？

- **理解 A（M2 内部两阶段）**：M2 包含全量 + 深入两阶段，M2 内部闭环。M4 是另一回事（基于 M2 深入分析结果做"代码改进建议"）。
- **理解 B（M2 全量 + M4 深入）**：M2 只做全量分析产出报告，深入分析属于 M4（M4 重新定义为"LLM 深入分析"，不是"改代码"）。

**奉孝倾向理解 A**——铲屎官说的是"利用 LLM 进行分析日志"，M2 的核心动作就是 LLM 分析日志，全量 + 深入都是 M2 内部两阶段。M4 改进可能是基于 M2 深入分析结果再做改进建议（如"M2 深入分析定位到根因 → M4 基于根因生成修复 diff"）。

→ 开放问题 Q1 让铲屎官拍板。

## 五、开放问题（请铲屎官确认）

### Q1: 两阶段都在 M2 内部，还是 M2 全量 + M4 深入？

- **选项 A**：M2 内部两阶段（全量 + 深入），M4 改进是另一回事
- **选项 B**：M2 全量 + M4 深入（M4 重新定义）
- **选项 C**：其他划分

### Q2: "全量"的边界是什么？

- 选项 A：按时间段（如最近 1 小时/1 天）
- 选项 B：按服务/模块分组
- 选项 C：按错误级别（ERROR/WARN）
- 选项 D：真正的"全量"（所有日志条目，token 成本爆炸风险）
- 选项 E：组合（如"最近 1 天的 ERROR+WARN 全量"）

### Q3: "客户要求时"具体怎么触发 Phase 2？

- 选项 A：用户在 UI 勾选某条日志条目 + 点"深入分析"按钮
- 选项 B：通过 API 调用（POST /analyze/deep）
- 选项 C：系统自动触发（如某错误高频出现自动深入分析）
- 选项 D：CLI 命令（运维场景）

### Q4: Phase 2 深入分析的输出形态？

- 选项 A：单条日志的深入分析报告（含根因假设 + 修复建议）
- 选项 B：包含修复 diff 建议
- 选项 C：是否回写到 M1 的 `llm_hypothesis` 字段（F001 spec §三 L145 已定义但说"候选阶段可空，confirmed 入库后必填"——M2 深入分析结果是否就是 M1 LogPoint 的 `llm_hypothesis`？）

### Q5: "二次/多次"深入分析的上下文累积方式？

- 选项 A：每次独立分析，不累积（无状态）
- 选项 B：累积上下文（对话历史模式，每次都基于前次结果）
- 选项 C：累积但带 TTL（如 30 分钟内累积，超时重置）

### Q6: 运行时日志的输入形态？

- 选项 A：用户上传日志文件（M2 离线 batch 处理）
- 选项 B：M2 从 M3 在线扫描的实时日志流里抽一段
- 选项 C：两种都支持

### Q7: 全量分析报告的存储位置？

- 选项 A：新表 `analysis_report`（M2 独立）
- 选项 B：复用 M1 的某张表
- 选项 C：文档存储（如 Markdown 文件 + 元数据表）

### Q8: LLM 成本控制策略？

- 选项 A：Phase 1 用便宜模型（GPT-4o-mini）+ Phase 2 用强模型（GPT-4）
- 选项 B：复用 M1 的 Redis 缓存（F001 spec §二 Unit C 缓存键设计）
- 选项 C：批处理 + 限流（限制每分钟调用数）
- 选项 D：组合
